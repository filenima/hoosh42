## 🔴 فوری (قبل یا حین Go-Live)

**۱. بیلد Production + اجرای PM2 (نه `next dev`)** — بنچمارک نشان داد حالت dev تا ~۳.۳GB رم مصرف و در ۱۵۰ کاربر OOM می‌شود؛ حالت production بدون کامپایلِ لحظه‌ای، پایدار و سبک (~۵۰۰MB-۱GB) است. روی سرور فقط `bun run build` + `next start` (PM2). *(راهنما: `VPS-IRAN-MIGRATION-GUIDE.md` بخش ۵)*

**۲. PostgreSQL در production به‌جای SQLite** — نویسنده‌ی واحدِ SQLite گلوگاه ذخیره‌سازیِ همزمان است (ثبت فاکتور/سند چند کاربر هم‌زمان). اسکیمای آماده `prisma/schema.postgres.prisma` + اسکریپت انتقال `scripts/migrate-to-postgres.sh` در پروژه هست؛ فقط باید انجام شود. *(همان راهنما، بخش ۴)*

**۳. PM2 کلاستر ۲ instance + `max_memory_restart: 3G`** — استفاده‌ی واقعی از ۴ هسته، تحمل خطا (افتادن یک instance = نیم‌سرویس، نه کل)، و ری‌استارت خودکار به‌جای مرگ OOM. *(فایل `ecosystem.config.cjs` — بخش ۵.۲ راهنما)*

**۴. Swap ۸GB روی VPS** — بیمه‌ی رایگان در برابر OOM-Killer؛ سرور در فشار به‌جای خاموشی فقط کند می‌شود. *(بخش ۳.۲ راهنما)*

**۵. تکمیل `.env` امن در production** — `JWT_SECRET` (بدون آن ورود در production خطا می‌دهد و نشست‌ها ناپایدار می‌شوند)، `CRON_SECRET` و `CHAT_INTERNAL_SECRET` قوی (پیش‌فرض‌های کد قابل حدس‌اند)، `NEXT_PUBLIC_APP_URL=https://hoosh.nobatime.ir`. کلیدها هرگز در گیت. *(بخش ۷ راهنما)*

**۶. خاموش‌کردن `ALLOW_SUPERADMIN_BOOTSTRAP` بعد از اولین ورود** — تا وقتی فعال است، هرکس که زودتر برسد می‌تواند سوپرادمین بسازد؛ بعد از bootstrap فوراً کامنت و ری‌استارت شود.

**۷. SSL + DNS دامنه (Nginx/certbot یا Caddy)** — بدون HTTPS نه زرین‌پال فعال می‌شود، نه اینماد، نه PWA نصب‌شدنی. *(بخش ۶ راهنما)*

**۸. فعال‌سازی درگاه زرین‌پال از پنل سوپرادمین** — مرچنت ثبت‌شده (`bd690050-…`) در تب «صورتحساب و پرداخت» + تست تراکنش واقعی کم‌مبلغ + تطبیق `NEXT_PUBLIC_APP_URL`/دامنه برندینگ با callback. *(بخش ۸ راهنما)*

**۹. بکاپ خودکار روزانه + کپی offsite** — `pg_dump` روزانه در cron + rclone به فضای ابری (مبین‌کلود/آروان) + نگهداری ۳۰ روزه + یک تست بازیابی. بدون این، یک خرابی دیسک = پایان کسب‌وکار. *(بخش ۱۰ راهنما)*

**۱۰. ایندکس‌های حیاتی Prisma برای مسیرهای پربار** — ستون‌های فیلتر/مرتبِ اندپوینت‌های اصلی: `Invoice(tenantId, status, issueDate)`، `JournalEntry(tenantId, date, status)`، `Notification(userId, readAt)`، `UserSession(token)`، `SupportTicket(tenantId, status)`. کوئری تجمعی داشبورد اولین جایی است که p95 بد می‌شود؛ ایندکس‌ها ارزان‌ترین بهبورند. *(بررسی سریع: `scripts/db-index-audit.sh`)*

**۱۱. Sentry با DSN واقعی** — `SENTRY_DSN`/`NEXT_PUBLIC_SENTRY_DSN` در `.env`؛ زیرساختش (`instrumentation.ts`، `lib/sentry.ts`) آماده است و فقط خاموش مانده. اولین ابزار برای دانستن «مشتری چه خطایی دید» قبل از تیکت.

## 🟠 کوتاه‌مدت (ماه اول بعد از Go-Live)

**۱۲. کش APIهای تجمعی داشبورد** — `GET /api/dashboard` با `Cache-Control: private, max-age=30` یا `unstable_cache` با TTL ۳۰-۶۰s + بی‌اعتبارسازی روی ثبت سند جدید. majority بار داشبورد تکراری است؛ کش، کوئری‌های تجمعی را حذف می‌کند.

**۱۳. محدودسازی/عقلانی‌کردن polling** — اعلان‌ها و داشبورد در فرانت حداقل هر ۶۰ ثانیه (نه <۱۰s) + توقف polling وقتی تب غیرفعال است (`visibilitychange`). این‌ها بارِ پس‌زمینه‌ی دائمی‌اند که با تعداد کاربر ضرب می‌شوند.

**۱۴. Redis برای rate-limit و کش مشترک بین instanceها** — الان rate-limit در حافظه‌ی پروسه است؛ با ۲ instance هر کدام شمارنده‌ی خودش را دارد (لایف‌تایم محدودیت ۲× می‌شود) و در ری‌استارت پاک می‌شود. Redis store مشترک + کش branding/settings مشترک. *(وابستگی `redis` در package.json موجود است)*

**۱۵. PgBouncer (یا تنظیم pool اتصال Prisma)** — با PostgreSQL، سقف اتصال‌ها را مدیریت کنید تا رشدِ ناگهانی کاربر، `max_connections` را پر نکند. ابتدا ساده: `connection_limit` در `DATABASE_URL`؛ سپس PgBouncer در حالت transaction-pooling.

**۱۶. gzip/brotli کامل + هدرهای کش استاتیک در Nginx** — ‏`/_next/static/` باید `Cache-Control: public, max-age=31536000, immutable` بگیرد؛ لندینگ/بلاگ با `proxy_cache` در Nginx بیمه شوند. پهنای باند ۱۰۰GB ماهانه را چند برابر شل‌تر می‌کند.

**۱۷. صف کار (BullMQ روی Redis) برای ایمیل/گزارش/پردازش سنگین** — ارسال ایمیل و تولید گزارش‌های زمان‌بندی‌شده (`/api/scheduled-reports/run`) از event loopِ درخواست‌ها جدا شود؛ در قطعی Gmail، صف دوباره تلاش می‌کند و کاربر منتظر نمی‌ماند. (ماژول‌های `email-queue`/`scheduled-reports` موجود پایه خوبی‌اند.)

**۱۸. لاگ ساخت‌یافته + چرخش لاگ** — ‏`pm2-logrotate` (در راهنما هست) + سطح‌بندی لاگ (env-based) + نگه‌داشتن خطاهای API با trace id در Sentry. برای عیب‌یابی تولیدی ضروری است.

**۱۹. مانیتورینگ خارجی + آلارم** — ‏UptimeRobot/سرویس مشابه روی `/api/health` و صفحه لندینگ؛ آلارم Sentry روی نرخ خطای بالای آستانه. «سایت down» را مشتری به شما نگوید.

**۲۰. سخت‌سازی چند-مستأجری (tenant isolation) در کوئری‌های سنگین** — ممیزی همه اندپوینت‌های گزارش/تجمعی: هر کوئری حتماً با `tenantId` فیلتر شود و در Prisma همه‌جا از همان کانکست scoped استفاده گردد؛ تست خودکار cross-tenant برای ماژول‌های جدید (invoices, journal-entries, CRM, inventory) در تست‌ها بگنجد.

**۲۱. تست بار دوره‌ای روی محیط production** — اجرای `bun scripts/load-test.ts` (بدون `--spike`) ماهی یک‌بار در ساعت کم‌بار و ثبت روند p95/RSS در یک برگه؛ روندها قبل از بحران معنا می‌شوند.

**۲۲. `output: "standalone"` یا Docker برای دیپلوی تکرارپذیر** — خروجی standalone پروژه ساخته می‌شود (`.next/standalone/`)؛ استانداردکردنِ «همیشه یک بیلد، همه‌جا یک‌شکل» + زمین‌سازی برای CI/CD و blue-green (اسکریپت `scripts/blue-green-deploy.sh` موجود است).

## 🟡 میان‌مدت (سه‌ماهه اول)

**۲۳. وب‌سوکت/SSE برای اعلان‌ها و داشبورد real-time** — جایگزینی polling با کانال push (وابستگی `socket.io-client` هست، سرور باید socket.io اضافه کند؛ یا SSE ساده در Next) → کاهش بار پس‌زمینه و تجربه زنده‌تر (فاکتور جدید، تیکت جدید، وضعیت پرداخت).

**۲۴. OCR فاکتور خرید/هزینه** — عکس فاکتور کاغذی → استخراج شماره/تاریخ/مبالغ → پیش‌پر شدن فرم ثبت هزینه. با سرویس OCR فارسی (یا LLM مالتی‌مودال) قابل پیاده‌سازی است؛ پرتکرارترین درخواست کاربران حسابداری.

**۲۵. اتصال بانکی (PSD2/open-banking ایرانی، شاپرک/شاپرلوک، یا صورت‌حساب بانکی)** — خواندن خودکار تراکنش‌ها برای مغایرت‌گیری بانکی؛ ماژول `bank-reconciliation` موجود است و داده‌ی واقعی بانک نیمی از کار مغایرت را حذف می‌کند. الزام‌آفرین حقوقی/فنی دارد — با یک بانک شروع کنید.

**۲۶. عمیق‌سازی مالیاتی/مودیان (کاربرگ سامانه مودیان)** — ماژول `modian` موجود است؛ ارتقا به ارسال خودکار صورتحساب الکترونیکی و کنترل اعتبار کد اقتصادی طرف حساب. برای بازار ایران، مزیت رقابتی اصلی SaaS حسابداری همین است.

**۲۷. API عمومی + مستندات عمومی** — ‏`app/api/open-api` و `api-keys` پایه‌اند؛ انتشار مستندات عمومی (مثلاً swagger) + نسخه‌بندی، اتصالِ نرم‌افزارهای جانبی مشتریان (POS/فروشگاه آنلاین) را باز می‌کند. با rate-limit و لاگ مصرف.

**۲۸. داشبورد عملکرد مدیر (Performance/Admin Dashboard)** — یک صفحه برای خودتان: کاربران فعال، نرخ تبدیل تریال→پلن، RPS، p95، خطاها، مصرف رم — داده‌ها همگی موجودند (superadmin → تحلیل‌ها). تصمیم‌گیری بدون حدس.

**۲۹. SSO/ورود با گوگل + دو-مرحله‌ای (۲FA)** — ‏`otplib` در پروژه هست؛ ۲FA برای سوپرادمین/کاربران حساس (دسترسی مالی!) و «ورود با گوگل» برای کاهش اصطکاک ثبت‌نام.

**۳۰. بهبود SEO/محتوای لندینگ و بلاگ** — ‏`robots.txt`/`sitemap` داینامیک و بلاگ موجودند؛ تولید محتوای منظم حسابداری (۷-۱۰ مقاله/ماه) + schema.org → کانال جذب ارزان. (داده بنچمارک: لندینگ در prod زیر ۵۰ms سرو می‌شود؛ گلوگاه جذب، سرعت نیست، محتواست.)

**۳۱. تست‌های E2E خودکار (Playwright) برای مسیرهای پول‌ساز** — ثبت‌نام → تریال → ثبت فاکتور → خرید پلن → callback زرین‌پال (sandbox). هر ریلیز بدون این تست‌ها، قمار است.

**۳۲. چند-نسخه‌ای واقعی دیتابیس (Prisma Migrate به‌جای db push)** — ‏`prisma db push` برای محیط توسعه خوب است؛ برای production با کاربر واقعی، تاریخچه‌ی migration (برگشت‌پذیر) لازم می‌شود. `prisma/schema.postgres.prisma` را مبنا قرار دهید و از اولین ریلیز، `migrate` را رسمی کنید.

**۳۳. CDN برای استاتیک‌ها و تصاویر بلاگ/گالری** — ‏CDN داخلی (ابرآروان/…) برای `/_next/static`، تصاویر `public/images` و پیوست‌ها؛ هم سرعت کاربر هم مصرف ترافیک ۱۰۰GB سرور.

## 🟢 بلندمدت (پس از تثبیت و رشد)

**۳۴. موبایل اپ (React Native/Expo یا Flutter)** — ‏PWA موجود نصب‌شدنی است اما برای استفاده‌ی روزمره‌ی حسابدار (اسکن فاکتور، اعلان، offline-first) اپ بومی با همان APIها (JWT + `/api/v1/*`) ارزش محصول را جهش می‌دهد.

**۳۵. Offline-first/PWA کامل با IndexedDB** — ‏`idb` در وابستگی‌ها هست؛ ثبت سند/فاکتور بدون اینترنت و sync بعد از اتصال — تمایز واقعی برای ایران با اینترنت ناپایدار.

**۳۶. Multi-region/High-Availability** — سرور دوم در دیتابیس اصلی دیگر (replication PostgreSQL + failover؛ اسکریپت `scripts/dr-failover.sh` پایه دارد) و Nginx در لبه. برای SLA سازمانی.

**۳۷. بکاپ رمزنگاری‌شده + جدول بازیابی فاجعه (DR Runbook)** — رمزنگاری فایل‌های بکاپ قبل از آپلود (age/gpg) + سناریونگاشته‌ی «سرور کامل سوخت: چند ساعت تا بازگشت؟» با تمرین فصلی.

**۳۸. Hardening امنیتی سازمانی** — ممیزی دوره‌ای با `scripts/security-audit.sh` و `scripts/pentest.sh` موجود، سیاست رمز/نشست (refresh token + revocation در `userSession`)، WAF ساده در Nginx (rate-limit global)، و bug bounty کوچک.

**۳۹. Marketplace/اکوسیستم افزونه** — زیرساخت `marketplace`/`app-marketplace` موجود است؛ API عمومی + webhooks (`app/api/webhooks` هست) را کامل کنید تا توسعه‌دهندگان شخص ثالث افزونه بسازند (گزارش سفارشی، اتصال‌های صنفی).

**۴۰. هوش مصنوعی مکمل کاربردی** — ماژول‌های AI موجود (تحلیل ناهنجاری، پیش‌بینی، دستیار) را از «نمایشی» به «روزمره» ببرید: دستیار ثبت خودکار تراکنش از توضیح فارسی، پیشنهاد کدینگ حساب، هشدار نقدینگی هوشمند. (زیرساخت `ai` و کرون `anomaly` آماده است.)

**۴۱. صورتحساب/اشتراک پیشرفته SaaS** — پلن‌های سالانه/ organization-based، تراکنش‌های تکرارشونده (دستور پرداخت)، فاکتور رسمی/مالی برای خودتان، و پنل self-service مشتری (مشاهده فاکتور/پرداخت).

**۴۲. گزارش‌ساز بی‌کد پیشرفته + خروجی اکسل حرفه‌ای** — ماژول‌های `reports-builder`/`custom-report-builder` موجودند؛ افزودن فرمول/جدول محوری/قالب چاپ رسمی ایران (با سربرگ و امضا) بیشترین درخواست کاربران حرفه‌ای است.

**۴۳. i18n کامل (انگلیسی/عربی) برای ورود به بازارهای همسایه** — زیرساخت next-intl موجود است؛ محتوای حسابداری فارسی/شمسی محور است، پس تصمیم تجاری/فنی جدی می‌خواهد — ولی مسیر رشد درآمد بعد از اشباع ایران همین است.

**۴۴. جداسازی مقیاس‌پذیر (micro-serviceهای سنگین)** — در ۱۰۰۰+ کاربر: گزارش‌های سنگین/OCR/AI روی سرویس صف جدا (کارگرهای BullMQ) و در صورت نیاز سرور جدا؛ اپ اصلی سبک بماند.
