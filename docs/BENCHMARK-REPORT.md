> **تاریخ اجرا:** ۵ شهریور ۱۴۰۵ (2026-09-05) — دو اجرای کامل روی همان سندباکس

## ۲. روش تست

### ۲.۱ محیط تست (سندباکس توسعه)

| مؤلفه | مقدار | توضیح |
|---|---|---|
| CPU | ۲ هسته | نصفِ VPS واقعی (۴ هسته) |
| RAM | ۴GB (بدون Swap مؤثر) | یک‌سومِ VPS واقعی (۱۲GB) |
| حالت اجرای Next | **`next dev` (Turbopack)** | ⚠️ کامپایل just-in-time — بدون بهینه‌سازی production |
| دیتابیس | SQLite (`db/custom.db`) | بدون سرور DB جداگانه |
| پروسه | یک `next-server` تنها | بدون PM2/cluster |
| تستر | `bun scripts/load-test.ts` روی همان ماشین | fetch بومی Bun + timeout ۲۰s |

> 🔴 **مهم برای تفسیر درست:** این محیط **عمداً بدترین حالت** است (کامپایل لحظه‌ای + رم کم + دیتابیس فایلی + تستر روی همان ۲ هسته). اعداد این گزارش **کف پایین** (lower-bound) عملکرد اپ‌اند، نه سقف آن.

### ۲.۲ مدل ترافیک (شبیه‌سازی رفتار انسانی)

- **۳۰٪ بازدیدکننده عمومی** (بدون لاگین): صفحه لندینگ SSR (`GET /`)، `/api/trust-badges`، `/api/testimonials`، `/api/blog/list`، `/api/branding`
- **۷۰٪ کاربر عضو** (لاگین‌شده با توکن JWT): توزیع درخواست‌ها —

| سهم | اندپوینت | نماینده‌ی |
|---|---|---|
| ۳۵٪ | `GET /api/dashboard` | صفحه اصلی اپ (سنگین‌ترین: تجمعی) |
| ۲۰٪ | `GET /api/v1/invoices?limit=5` | ماژول فاکتورها |
| ۱۵٪ | `GET /api/accounting/journal-entries?limit=100` | اسناد حسابداری |
| ۱۵٪ | `GET /api/accounting/chart-of-accounts` | کدینگ |
| ۱۵٪ | `GET /api/notifications` | اعلان‌ها (پولینگ) |
| ~۱۰٪ اضافی | یک اندپوینت عمومی تصادفی | رفتار واقعی عضوها |

- **زمان تفکر (think time):** ۱.۵ تا ۵ ثانیه تصادفی بین اکشن‌ها + شروع تدریجی ۰-۲ ثانیه‌ای هر کاربر مجازی (VU)
- **فازها:** warmup (۵ VU / ۲۰s) → steady (۵۰ VU / ۶۰s) → peak (۱۰۰ VU / ۱۲۰s) → spike (۱۵۰ VU / ۶۰s — فقط با فلگ `--spike`)
- **نمونه‌برداری منابع:** هر ۲ ثانیه RSS پروسه از `/proc/<pid>/status` و CPU از `/proc/stat`
- دو اجرا: **اجرای اول** (فازهای ۵/۵۰/۱۰۰ + اسپایک ۱۵۰) و **اجرای دوم** (۵/۵۰/۱۰۰ بدون اسپایک؛ دیتای JSON نهایی از همین اجراست).

### ۳.۲ تحلیل (صادقانه و فنی)

۱. **p50 در هر دو اجرا یکی است (۱۰-۲۲ms):** منطق اپ (JWT → Prisma → SQLite → JSON) ذاتاً سریع است؛ حتی وقتی سرور در بدترین وضعیت بود، نصفِ درخواست‌ها همچنان زیر ~۲۰ms جواب گرفتند.
۲. **چرا اجرای دوم بدتر شد؟** نمونه‌بردار CPU نشان می‌دهد در steady-50 و peak-100 پردازنده **۹۴-۱۰۰٪** قفل بود. علت ترکیبی: (الف) سرور بعد از OOM اجرای اول توسط watchdog ری‌استارت شده بود و **کش کامپایل Turbopack سرد بود** — یعنی dev-server بجای serve، مدام در حال کامپایلِ مجددِ مسیرها بود؛ (ب) تستر هم روی همان ۲ هسته اجرا می‌شد (رقیق مستقیم CPU)؛ (ج) بدون PM2/ری‌استارتِ بین فازها، فشار انباشته شد. **این دقیقاً همان رفتاری است که از حالت development انتظار می‌رود و در production وجود ندارد** (کامپایل از قبل انجام شده — `next start` فقط serve می‌کند).
۳. **خطاهای اجرای دوم (۱۵.۷٪ → ۳۳.۸٪):** تقریباً تماماً timeoutهای ۲۰ ثانیه‌ای AbortController (max ≈ ۱۹.۹s) و اتصال‌های ردشده به سرورِ CPU-قفل‌شده‌اند — نه خطای منطقی 5xx اپ. نکته instructive: حتی در این وضعیت، پاسخ‌های موفق p50=15-18ms ماندند.
۴. **لندینگ SSR (p50=۱۲۹ms، p95 تا ۱۶.۹s):** بارِ کامپایل dev روی سنگین‌ترین صفحه، صف‌های طولانی ساخت. در بیلد production این صفحه استاتیک/prebuild می‌شود و p95 واقعی آن معمولاً زیر ~۱۰۰ms است.
۵. **نمونه‌بردار حافظه اجرای دوم نامعتبر است** (PID اشتباهی توسط `pgrep` گرفته شد و RSS~3MB گزارش شد) — حافظه را از **اجرای اول** ببینید: **peak RSS ≈ ۳.۲۸GB روی ۴GB** در آستانه‌ی OOM؛ متناسب با فاز رشد می‌کرد (۵→۱۵۰ کاربر = رشد خطی RSS).
۶. **شکست در پهنای دُم، نه میانگین:** در هر دو اجرا «میانه» عالی و «دم» متغیر است. مهندسی production یعنی مدیریت همان دم (کش/cluster/ایندکس)، نه بازنویسی هسته.

## ۴. نقطه شکست: OOM در ۱۵۰ کاربر (اجرای اول — یافته‌ی مستند)

### چه اتفاقی افتاد؟

1. در فاز spike-150 تعداد کاربران همزمان ۵۰٪ بالاتر از peak-100 شد.
2. پروسه‌ی `next-server` (که در dev، کامپایلر Turbopack و ماژول‌های کامپایل‌شده را در حافظه نگه می‌دارد) رشد کرد تا **RSS ≈ ۳.۲۸GB** روی ماشین ۴GB.
3. کرنل لینوکس **OOM-Killer** را فعال کرد و پروسه‌ی پرحافظه (خودِ سرور اپ) را **kill** کرد → سایت فوراً ۱۰۰٪ خطا داد.
4. ناظر سندباکس (watchdog) پروسه را حدود **۲ تا ۳ دقیقه** بعد دوباره بالا آورد — سرور برگشت ولی **کش کامپایل سرد** بود؛ همین حالتِ سرد بود که اجرای دوم را (بخش ۳.۲) بدتر نشان داد.

### چرا این شکست «مرز واقعی» نیست؟

| عامل | در سندباکس | در VPS تولیدی |
|---|---|---|
| کامپایلر در حافظه | Turbopack dev — پایه ~۱-۱.۵GB + رشد با هر مسیر | **بیلد از قبل انجام شده** — `next start` فقط serve؛ پایه ~۵۰۰MB-۱GB |
| Swap | عملاً نبود → OOM-Killer فوراً ضربه زد | ‏۸GB Swap + `vm.swappiness=10` → به‌جای kill، کندیِ موقتی |
| رم کل | ۴GB | **۱۲GB** (۳ برابر) |
| محافظ | فقط watchdog بیرونی | PM2 `max_memory_restart: 3G` (ری‌استارت خودکار قبل از مرگ) |

> 📌 **نتیجه:** «۱۵۰» مرزِ *این سندباکس در حالت dev* است. دلالت مفیدش: **حافظه اولین منبعی است که تمام می‌شود** — نه CPU و نه دیسک؛ طراحی production باید حافظه‌محور باشد (بخش ۶). ضمناً درس عملیاتی اجرای دوم: بین تست‌های بار، سرور را ری‌استارت کنید و تستر را ترجیحاً از ماشین جدا اجرا کنید — روی VPS بعداً همین کار را بکنید (بخش ۷).

## ۵. استنتاج برای سرور واقعی (VPS مبین‌هاست: ۱۲GB RAM / ۴ هسته)

### ۵.۱ تفاوت‌های محاسبه‌شده dev ↔ prod

| بُعد | سندباکس (اندازه‌گیری‌شده) | VPS تولیدی (استنتاج) | ضریب بهبود |
|---|---|---|---|
| کامپایل | JIT در هر مسیر (CPU ۹۴-۱۰۰٪ حتی با ۵۰ کاربر) | از پیش بیلدشده — CPU صرف پاسخ‌گویی | p95: ~۵-۲۰× |
| React | توسعه‌ای | production (بدون devtools/هشدار) | ~۱.۵-۲× |
| RAM | ۴GB، OOM در ۳.۲۸GB | ۱۲GB + Swap + PM2 restart-guard | ~۳× + ایمنی |
| CPU | ۲ هسته (+ تستر روی همان!) | ۴ هسته (تستر جدا) + PM2 cluster ۲ instance | ~۲-۳× |
| DB | SQLite (نویسنده واحد) | **PostgreSQL 16** (نویسنده همزمان + pool) | نوشتن همزمان: چند برابر |

### ۵.۲ تخمین ظرفیت (ریاضی و قابل دفاع)

- **حافظه:** پایه‌ی prod حدود ~۱-۱.۵GB (۲ instance در cluster ≈ ۲×۷۵۰MB)؛ هر اتصال/درخواست فعال ۲-۵MB معنوی. با ۱۲GB: ~۸GB قابل تخصیص به ترافیک ⇒ مرز عملی ~۴۰۰-۷۰۰ اتصال همزمان فعال (بعدش Swap/کندی، نه کرش).
- **CPU:** در سندباکسِ قفل‌شده هم p50=15-18ms بود؛ در prod با ۴ هسته و بدون کامپایل، ظرفیت API با p50≈۱۰-۲۰ms بالای **۱۵۰-۲۵۰ RPS پایدار** است. با think time انسانی (۱.۵-۵s) هر کاربر ~۰.۲-۰.۳ RPS تولید می‌کند ⇒ ۵۰۰ کاربر ≈ ۱۰۰-۱۵۰ RPS — داخل محدوده.
- **دیتابیس:** خواندن با ایندکس‌ها تا صدها کاربر بی‌مشکل؛ **نوشتن** (ثبت فاکتور/سند) و **تجمعی داشبورد** زودتر خط می‌کشند.

**اعداد تخمینی نهایی برای ۱۲GB/۴c:**

| سنجه | تخمین محافظه‌کارانه | توضیح |
|---|---|---|
| کاربران همزمان پایدار | **۳۰۰-۴۰۰** | اگر (به‌اشتباه) SQLite و تک-instance بمانید |
| کاربران همزمان پایدار | **۴۰۰-۶۰۰** | PostgreSQL + بیلد prod + PM2 cluster ۲ instance + کش |
| RPS پایدار | ~۱۵۰-۲۵۰ | p95 زیر ۳۰۰ms |
| کاربر فعال روزانه (غیرهمزمان) | **۲٬۰۰۰-۵٬۰۰۰+** | الگوی ورود پلکانی واقعی |
| ۱۰۰ کاربر همزمان | ✅ **راحت و با حاشیه امن** | رم کل انتظاری <۴GB از ۱۲GB |

### ۵.۳ چه چیزی «اول» کند می‌شود؟ (ترتیب اشباع در production)

1. **کوئری‌های تجمعی داشبورد/گزارش‌ها** (`/api/dashboard`، سود/زیان، ترازنامه): تجمع روی journal-entries/invoices — اولین جایی که p95 رشد می‌کند. راه‌حل: ایندکس + کش.
2. **نوشتن همزمان DB:** ثبت فاکتور/سند/پرداخت با ۱۰۰+ ذخیره‌ی همزمان — دلیل اصلی PostgreSQL.
3. **فواصل polling اعلان‌ها/داشبورد:** بار پس‌زمینه دائمی = کاربران × (۶۰/فاصله) RPS — باید محدود/هوشمند شود.
4. **SSR لندینگ در موج تبلیغاتی:** در prod بسیار بهتر از dev است؛ برای موج‌های بزرگ، کش لبه (Nginx proxy_cache / ISR).

| ۴ | **Swap ۸GB** + `vm.swappiness=10` | 🔴 حیاتی | OOM عملاً بی‌اثر؛ کندی جای خاموشی |
| ۵ | **ایندکس‌های Prisma** روی فیلتر/مرتبِ پرکاربرد (Invoice: tenantId+status+issueDate؛ JournalEntry: tenantId+date+status؛ Notification: userId+readAt) | 🟠 کوتاه‌مدت | p95 تجمعی چند برابر |
| ۶ | **کش داشبورد/عمومی:** `GET /api/dashboard` با TTL ۳۰-۶۰s (`unstable_cache`/Cache-Control) + کش لبه Nginx برای لندینگ/بلاگ | 🟠 کوتاه‌مدت | حذف majority کوئری تجمعی تکراری |
| ۷ | **محدودسازی polling:** اعلان‌ها ≥۶۰s؛ توقف در تب غیرفعال (`visibilitychange`) | 🟠 کوتاه‌مدت | کاهش ~۵۰٪ بار پس‌زمینه |
| ۸ | **Nginx gzip/brotli + `proxy_cache`** و `Cache-Control: immutable` برای `/_next/static/` | 🟠 کوتاه‌مدت | پهنای باند + مقاومت موج تبلیغاتی |
| ۹ | **Rate-limit با store مشترک (Redis)** — الان in-memory است؛ با ۲ instance شمارنده‌ها جدا و ناقص‌اند | 🟡 میان‌مدت | امنیتِ درست در کلاستر |
| ۱۰ | **پایش:** `pm2 monit` + Sentry (DSN در `.env`) + تست بار دوره‌ای (بخش ۷) | 🟡 میان‌مدت | دید واقعی به‌جای حدس |
| ۱۱ | Redis برای کش/نشست مشترک + PgBouncer | 🟢 بلندمدت (۵۰۰+) | مقیاس افقی DB و کش |
